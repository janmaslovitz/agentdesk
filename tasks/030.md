Goal: re-layout and simplify the Git and Build sections of the project page.
Where: agentdesk/web/index.html (Git section ~L364-386, Build section ~L387-392, JS buildShow/buildLoad/buildGo ~L470-494), core.py BuildJob/build_job (~L3246) and build endpoints in server.py (~L2006, ~L2108), tests in tests/.

1. Layout: Git section takes 50% of the page width; the Build section sits in the other 50% in the same row, compact so it doesn't add height (collapse the log into a <details> or a small fixed-height scroll box; keep headline buttons small). On narrow windows (<900px) they stack. Keep all existing Git functions working unchanged.

2. Build redesign (clearer): 
 - A "Version" selector: the existing release tags (vX.Y.Z, newest first) plus a "New build (next)" entry that proposes the next patch version from CHANGELOG/__version__ and lets the user edit it. The selected version is the build's current target.
 - A checklist of finished tasks (state.json status done, with branch auto/<id>): checkbox + id + title + merged/unmerged badge. Tasks already contained in the selected base ref are shown checked+disabled ("already in"). Tasks finished since the last tag are checked by default; "Select all / none" links.
 - "Build" button: creates (or resets) an integration branch/worktree `build/<version>` from the base branch, merges the checked unmerged auto/<id> branches into it (stop and report clearly on a conflict, leaving base and the task branches untouched), then runs the existing build command on that worktree. Never modifies the base branch or pushes. Keep "Clean + rebuild", Stop, Open folder, custom build as they are (compact, in a small menu if needed).
 - Show a short result line: version, tasks included, success/failure, link to open the folder. Remember the last selection per project (data file, not git).
 - The list refreshes when a task finishes (as the Needs attention/queue refresh does); no extra polling load - reuse the existing poll, and don't poll the build log unless a build runs.
3. API: GET /api/p/<slug>/build returns also `versions` and `tasks` (id,title,merged,in_base,default_checked); POST build accepts `version` and `tasks` (list of ids, validated against known done tasks). Invalid input -> 400 with a message.
4. Tests for: task listing (merged/in-base flags), selection validation, integration-branch creation with a clean merge and with a conflict (base untouched), API validation. Use `pytest tests`. CHANGELOG Unreleased entry. README build section update.
Constraints: don't break existing build flow for projects with a build command in project.toml; no secrets; don't push or release. Done when tests pass and the page renders (check HTML structure, no JS syntax errors - e.g. run the script through node --check if available).
