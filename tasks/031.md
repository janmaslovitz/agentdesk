Goal: every release tag (v*) gets Windows, macOS and Linux downloads on its GitHub Release, built by CI (we can't cross-build from the Windows dev machine).
Today: Windows only. build_exe.ps1 + agentdesk.spec (PyInstaller) -> dist/AgentDesk, build_installer.ps1 (Inno Setup) -> AgentDesk-Setup-x.y.z.exe, release.ps1/tools/release.py bump+tag. Source install for mac/linux exists (install.sh, agentdesk.sh). Window = pywebview, tray = pystray, claude-agent-sdk bundles the CLI.
Do:
1. Read agentdesk.spec / build_exe.ps1 and make the spec cross-platform (no Windows-only paths/icons/hiddenimports unguarded; .ico only on win32, .icns optional on darwin). Add build_unix.sh that runs PyInstaller from a venv and packs: Linux -> AgentDesk-<ver>-linux-x86_64.tar.gz, macOS -> AgentDesk-<ver>-macos-<arch>.zip (a .app bundle if simple, else the folder). Version read from agentdesk/__init__.py.
2. .github/workflows/release.yml: on push of tag v*, matrix [ubuntu-22.04 (also install webkit2gtk/gtk libs pywebview needs), macos-latest, windows-latest]; run `pytest tests` once (ubuntu), build each, and attach assets to the release for the tag (create it if missing, notes from CHANGELOG section of that version via a small script in tools/). Windows job keeps the existing installer name AgentDesk-Setup-<ver>.exe (install Inno Setup via choco) - the in-app updater picks AgentDesk-Setup*.exe, so do not rename it. Also add workflow_dispatch to rebuild a given tag. Use only official actions pinned by major version; no secrets beyond GITHUB_TOKEN.
3. Fix platform assumptions found while doing this (server.py/core.py: paths, creationflags, os.startfile, shell=PowerShell uses) only where they break the packaged app on Linux/macOS; keep Windows behaviour identical. The in-app updater stays Windows-only: on mac/linux the update badge should just link to the release page (small change in update_status/UI, with a test).
4. README: short "Downloads" section (Windows installer, macOS zip, Linux tar.gz, note that macOS builds are unsigned: right-click Open) and how CI releases work. CHANGELOG Unreleased entry.
5. Tests: what can be tested offline (spec/script syntax check, version extraction, release-notes extraction from CHANGELOG, updater link on non-Windows). `pytest tests` must pass on Windows.
Constraints: don't push, don't tag, don't run the workflow; we can't verify the CI here, so keep it simple and say in your report exactly what is untested. YAML must be valid (parse it with python yaml if available).
