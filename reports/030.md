## Worker summary

The Git and Build sections now share one row on the project page, and Build makes a versioned build from the tasks you tick. All 355 tests pass (`pytest tests`), including 6 new ones in `tests/test_build_versions.py`. The page script passes `node --check` and the page's HTML tags all close correctly. I did not open the page in a browser, so I haven't seen the new layout.

**Layout:** Git and Build each take half the width and stack under 900px. The Git controls are unchanged; the only addition is that a successful "Merge into base" also refreshes the Build list so its badges stay current. In Build, the log is folded under "Log", the task list is a small scroll box, and the headline buttons are small: Build, Stop, Open folder. The old controls (build a branch or commit as it is, Clean + rebuild, Custom build) are in a "More ▾" menu and work as before.

**Build redesign:**
- **Version:** a selector with "New build (next)" first, then the `vX.Y.Z` tags, newest first. The next version is the patch after the newest of the tags, the top version in `CHANGELOG.md` and `__version__`; it is 1.2.2 for this repo, and you can edit it. Picking a tag builds from that tag instead of the base branch.
- **Task list:** done tasks whose `auto/<id>` branch still exists, with a merged/unmerged badge. Tasks already in the base are ticked and greyed out ("already in"). Tasks finished since the last tag are ticked by default, and there are Select all / none links.
- **Build button:** it resets `build/<version>` in the existing build folder (`<project>/build/src`), merges the ticked branches one at a time, then runs the build command. That command is `[build] command` from `project.toml` if set, otherwise `build_exe.ps1`.
- **Conflicts:** a conflict aborts the merge and nothing is built. The result line names the task and the conflicting files. The base branch and the task branches are never changed, and nothing is pushed.
- **Result and memory:** a one-line result shows the version, the tasks, ok/failed and an "open folder" link. The last choice is saved per project in `<project>/build/selection.json`.
- **Polling:** the list reloads when a task finishes or a build ends, using the existing poll. During a build, only status and log are fetched (`?lite=1`), once a second.

**API:** `GET /api/p/<slug>/build` now also returns `versions` and `tasks`, and `?version=` picks a version. `POST` accepts `version` and `tasks`; a bad version, a non-list, or an id that isn't a finished task with a branch returns 400 with a message. A POST without `version`/`tasks` behaves exactly as before.

I also added a "The Build panel" section to the README and Added/Changed entries under Unreleased in the CHANGELOG.

On this project the list will currently be empty. Tasks 023–029 have `auto/` branches, but this project's `state.json` has no entries for tasks 020 and later, so none of them count as done. The list follows the brief's "status done in `state.json`" rule; tasks that aren't recorded there won't appear.

NOTES:
- Versioned builds use branch `build/<version>` checked out in the existing build folder `<project>/build/src`; the last choice is in `<project>/build/selection.json`. `core.build_plan` / `core.check_build_selection` supply the list and the validation.
- `GET /api/p/<slug>/build?lite=1` skips the version/task git calls; the UI uses it only while a build runs.
- The task list needs `state.json` entries with status `done` and an existing `auto/<id>` branch; tasks run outside AgentDesk's own state (e.g. 020+ here) won't appear.
