## Worker summary

The failing check was caused by my test, not by `build_unix.sh`. On the check machine, `bash` on PATH is `C:\WINDOWS\system32\bash.exe`, the WSL launcher. With no Linux distro installed it only prints "no distributions installed" and exits 1, so the syntax check failed without ever reading the script.

**Fix:** in `tests/test_release_ci.py`, a new `working_bash()` helper picks the bash used for the syntax check. On Windows it tries Git's own bash first, found through `git --exec-path`, then whatever `bash` is on PATH. It only uses one that actually runs `echo ok`. If none works, the test is skipped rather than failed. The `bash -n` check itself is unchanged.

**Verified:** I put `C:\WINDOWS\system32` first on PATH to recreate the failing setup. The test then picked Git Bash and passed, and that bash still rejects a deliberately broken script. The full `python -m pytest -q -x` passes in that setup: 370 tests. Nothing else changed, so my earlier summary still stands, including the list of what is untested in CI.

NOTES:
- On Windows, `bash` on PATH can be System32's WSL launcher, which fails when no distro is installed; tests needing bash should use Git's bash (`tests/test_release_ci.py::working_bash`).
- Release CI is `.github/workflows/release.yml` (tag push or manual run with a tag; draft → assets → publish); macOS/Linux builds come from `bash build_unix.sh`, and `tools/release.py notes <ver>` gives the release notes.
- Off Windows the updater links to the release page (`update_status` `link_only`/`page`, `POST /api/update/open`); the packaged app's default data folder is `core.user_data_dir()`.
