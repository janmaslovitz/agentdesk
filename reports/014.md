# 014: Bash approval card in the chat doesn't close after the answer

Branch `auto/014` at e514501; tiers standard.

## Brief

GOAL (task 014): a Bash/PowerShell approval card in the chat must disappear after Allow once / Always allow / Deny, with the command running once (Allow) or not running (Deny), and with no second prompt. A card whose request already ended (timeout, reset) must disappear on the next poll.

LIKELY CAUSE (read-only, verify before fixing): in agentdesk/web/index.html, `answer()` (~line 530-534) sets `pendingKey = ""` and then calls `pollPending()`. When the server's list is now empty, `key` is also "" (line 517), so the guard at line 518 (`if (key === pendingKey) return;`) returns early and the DOM is never cleared. Later polls also see "" === "" and return, so the stale card stays until a new approval arrives. Confirm this in the clone (e.g. Allow the last card and watch #pending). The 404 path (server.py ~1068, "that request isn't waiting any more") goes through the same early return, so it hits the same bug.

## Worker summary

I fixed the page so an approval card now clears even when the server's pending list is empty. I didn't run it in a browser, so that part is untested. The full pytest run passed (130 tests) before my last edit, which only restored the line endings in `index.html`. I re-ran `test_chat.py` afterwards and it passes (28 tests).

**Root cause.** The brief's suspected cause is real. In `index.html`, `answer()` reset `pendingKey` to `""`, and an empty server list also gives the key `""`. The guard `if (key === pendingKey) return;` then returned early, so the DOM was never re-rendered on an empty list. The 404 path went through the same early return.

**Two other findings.**
- **Server race:** `Approvals.resolve` used to leave the item listed until the SDK loop got round to `ask()`'s `finally`. A poll right after the click could therefore still list the card. This fix was already in the worktree's `server.py` when I started (not committed, not mine); it pops the item synchronously. The existing `test_answered_card_leaves_the_list_at_once` covers it.
- **Chat reset:** `Chat.reset` calls `deny_all()` on the same `Approvals` object, so ids don't go stale there.

**Changes.**
- `agentdesk/web/index.html`: `pendingKey` now starts as `null` and is set to `null` (not `""`) in `answer()` and on chat switch. The next poll then always renders, including an empty list. No re-render happens while the id set is unchanged, so typing in the prefix box is safe. I edited the file byte-wise because it has mixed line endings.
- `tests/test_chat.py`: two new tests.
  - `test_page_rerenders_an_empty_pending_list` is a source-text check of `index.html`, not a run of the JS. It fails before the fix.
  - `test_http_answer_leaves_empty_list_and_second_answer_404s` is a pure-Python endpoint test: Deny leaves an empty pending list, and a second answer gets the 404 "isn't waiting" error. It would not have failed before the fix.

**Tested.** The existing tests already cover Allow once (command runs once), Deny, Always allow (the allow-list grows and the same prefix stops asking), timeout and reset.

**Not tested.** I did not do a browser run or reproduce the stuck card in a live clone, and the JS itself has no automated test. To check it by hand, use a temp `AGENTDESK_HOME` on a port other than 8765. Trigger a Bash approval, click Allow once, Deny or Always allow, and confirm `#pending` empties. Then wait for a request to time out and confirm its card disappears on the next poll.
